- 2026-07-21: **BC50 integration density is now a setting (`BC50IntegrationPoints`, default 10000), with its accuracy pinned by a test.** The x = 1-t² substitution made the integrand smooth, so the panel count can be cut hard; the setting exposes that trade. Measured worst case over four parameter sets against an independent reference: 4e-13 relative error at 10000 panels, 3e-10 at 1000, 4e-7 at 100 — 1000 panels still beat what the pre-substitution code achieved at 10000, at a tenth of the work. New ctest `BC50AccuracyTest` asserts the accuracy per density, that the setting actually reaches the integration, and that an unset or zero value falls back to the default instead of turning the step into infinity (the CLI and tests run without the settings registry). Writing it caught a real mistake: the accuracy figures I had put in the tooltip came from ONE parameter set and understated the worst case by 600x. The per-site magic step sizes (1e-4/1e-5/1e-6) are gone; all BC50 integration now runs at one configurable density. Two rules added to CLAUDE.md as a result — keep development context out of reader-facing text, and quote numbers from a spread rather than a single sample.
- 2026-07-21: **BC50 integrals now run under the substitution x = 1-t², accuracy from ~1e-8 to ~1e-13.** Every BC50 integral is over the saturation fraction x in [0,1], where alpha = x/(1-x) diverges; the integrands inherit that as sqrt-type endpoint behaviour (BC50_Y vanishes like sqrt(1-x), the 1:1/1:2 free guest grows like (1-x)^-0.5). On a uniform mesh that caps ANY closed rule at O(h^1.5) and forces the non-finite-endpoint fallback. With x = 1-t² (dx = -2t dt) the square root is absorbed exactly and the transformed integrand is smooth, so Simpson recovers its full O(h^4) — for BC50_Y the substitution is analytically 2·t²·sqrt(b11²t² + 4b12(1-t²)). New `BC50::IntegrateSaturation()` wraps it; all 27 call sites converted. Measured against an independent high-accuracy reference: relative error 3.3e-8 -> 7.0e-13, 4.8e-8 -> 2.0e-13, 1.1e-9 -> 5.7e-13 (factor 1.9e3 to 2.4e5). The values now match the reference to 12 digits. Step size left at 1e-4, but the substituted integrand reaches machine precision already at 1e-3 (10x fewer panels) and 6e-10 at 1e-2 (100x fewer, still 80x better than the old direct integration) — an open speed lever for the Monte-Carlo path, where BC50 runs once per resampled model. A change of variables cannot create a value that does not exist: `IItoI`'s divergent breakdown integrals stay divergent and truncation-dependent. Found on the way: `IItoII::Format_BC50` contains a HAND-ROLLED copy of the same quadrature with the same overlap defect and its own OpenMP pessimisation; left untouched and marked TODO because its cross-terms are an approximation needing a modelling decision. Test set unchanged; `ReferenceProjectsTest` 12/2.
- 2026-07-21: **`SimpsonIntegrate` was not integrating what it claimed — three defects, now pinned by tests.** The loop advanced `x` by `i/increments` while using `delta` as the panel width, so (1) the panels OVERLAPPED by ~delta^2 each; over ~1/delta panels that is an **O(delta) relative error — first order**, which masked Simpson's O(h^4) entirely (measured: `int_0^1 x^3 dx = 0.24925` instead of 0.25, i.e. 0.3 % off on a cubic that Simpson integrates EXACTLY); (2) `i/increments` spans a unit length regardless of `upper-lower`, so any interval other than length 1 integrated the **wrong range** (`int_0^10 x dx` returned 5.04 instead of 50 — harmless in practice only because all 27 call sites are BC50 integrals over [0,1]); (3) a step larger than the interval produced no panels at all. Replaced by an exact composite Simpson whose last panel closes on `upper` itself. Fixing the tiling exposed a defect the bug had been HIDING: the BC50 integrands live on the half-open [0,1) — at complete saturation alpha = x/(1-x) diverges — so a closed rule now evaluated the singular endpoint and returned NaN/inf for `ItoII::BC50`, `IItoII::BC50_A0` and most of `Format_BC50` (live in every titration model's `ModelInfo`). Panels whose endpoint is not finite are therefore integrated by the open 2-point Newton-Cotes rule, the standard treatment for an integrable endpoint singularity; the old code only ever looked correct there because it never reached x=1. **BC50 itself changes by ~1e-4 relative (0.01 %)** — well below the 3-4 significant digits reported, and toward the true value (independently confirmed on the operator's reference system: 149.283 -> 149.301 muMol). The `Format_BC50` BREAKDOWN is a different story and is now tracked as an open item: for `IItoI` the free host in `ABPair` is x-independent, so B ~ 1/(1-x) and `int B dx` DIVERGES logarithmically — BC(B)0, BC(AB)0, BC(A2B)0, BC(A0)0 and BC(B0)0 are fixed only by where the quadrature truncates and all five moved by the identical factor 1.2738 (+27.4 %). Those were never well-defined numbers; the old step size just happened to pick one. `ItoII`'s counterparts are integrable (B ~ (1-x)^-0.5) and shifted 0.3-1.0 %. New ctest `QuadratureTest` (9 cases: polynomial exactness, integration range, convergence order, both endpoint-singularity kinds, degenerate arguments) fails 4/9 against the old implementation. Test set otherwise unchanged; `ReferenceProjectsTest` stays at 12/2.
- 2026-07-21: **Monte-Carlo results widget 15x faster (10.4-13.0 s -> 0.69 s for a 2000-step run on the fixed 1:1/1:2 model).** The operator symptom was a progress bar that reached ~10 % and then froze longer than the simulation itself, only for FAST models. Phase timing localised it to `ResultsWidget`, and a new offscreen harness `benchmark_mcwidget` (first test target linking the GUI layer; runs MC headless via JobManager, then builds the real widget under PhaseTiming) bisected it to `MonteCarlo2BC50_1_2` -> `BC50::ItoII::BC50` -> `SimpsonIntegrate` — 2000 numerical integrations, one per resampled model. Removed; the loop is deliberately serial now and, as a side effect, deterministic (the reduction summed in a nondeterministic thread order, so the old code could differ run-to-run in the last digits). Values agree to 15 significant digits. This also resolves the contradiction recorded in the handoff: the render chain (`Clone`, `ImportModel`, `MakeHistogram`, `MakeScatter`) was never the cost — 30 ms total — and scripted models were fast only because they do not override `AnalyseMonteCarlo` with a BC50 integration. - 2026-07-19: **Randomised cross-validation of the cubic solvers — and the historical default is inaccurate.** `test_cubicsolver::testRandomisedAgreementWithReference` samples 4000 seeded random cubics from BOTH families that share `MinCubicRoot` (1:1/1:2 guest cubic, 2:1/1:1 host cubic) over lg K in [0,9], H0 in [1e-6,1e-1] and G0/H0 in [0,5], and compares both variants against a long-double bracketed bisection reference, so a disagreement also says which one is wrong. Result: analytic max relative error **2.6e-9**, historical Newton max **0.217**, off by more than 1e-4 in **348 of 4000** samples. The sweep also found the closed form itself failing at extreme constants (a = beta11*beta12 ~1e17 vs d ~ -1e-1 gave -0.27 where the root is 3.8e-10), so `AnalyticCubicRoot` now uses the closed form only as a SEED and refines it with a safeguarded Newton inside a guaranteed sign-change bracket — correct regardless of the seed. Costs ~3.5% (255 -> 264 ns) and is still 1.64x faster than the Newton default (434 ns). Caveat before promoting it to default: the sampled space includes unphysical corners, so 8.7% of samples is not 8.7% of real fits — but the affected models (nmr_ItoI_ItoII, nmr_IItoI_ItoI, fl_*, uv_vis_*) all share this solver.

- 2026-07-19: **Closed-form cubic root solver as an opt-in variant** (`CubicSolver::setMethod`, `AnalyticCubicRoot`). `MinCubicRoot` is not a closed form despite the name — it runs three Newton searches to pick a root — and it has two real defects: the third "root" iterates on the DERIVATIVE using the derivative as its own derivative, so the Newton step degenerates to `x -= 1` (a linear scan, capped at 100 steps) and the result is not a root at all; and two branches of its root selection are unreachable, so it returns the first non-negative of roots 1/2 rather than the minimum. Added a Cardano/trigonometric implementation returning the smallest non-negative root. It is selectable and **defaults to the historical Newton path**, so published fit results stay reproducible. Measured on `nmr_ItoI_ItoII` (min of 5 release runs): 439.9 -> 255.3 ns per point-eval = 1.72x; together with the FillDesign fix 620.7 -> 255.3 ns = 2.43x. It is also more accurate: at G0 = 0 the analytic solver returns 0 where Newton returns ~3e-9, because Newton stops at |f(x)| < 1e-8 ABSOLUTE regardless of scale. New ctest `test_cubicsolver` (residual check on both discriminant branches, agreement with Newton within its own 1e-8 accuracy over a grid of titration cubics, default-is-Newton guard). `benchmark_scriptengine analytic` switches the variant on.
- 2026-07-19: **`nmr_ItoI_ItoII` concentrations 1.44x faster** (620.7 -> 431.0 ns per point-eval, min of 5 release runs, A/B against the unmodified file). `FillDesign()` solved TWO cubics per data point — `HostConcentration` and `GuestConcentration` — and built a `QList<qreal>` of the constants twice per point inside the fit hot loop. Note `MinCubicRoot` is not a closed form despite the name: it runs three separate Newton searches (one per root) to pick the smallest, so the model was doing six root searches plus two heap allocations per point — which is why the general numerical `nmr_any` outran it. Now the constants list is hoisted and only the guest cubic is solved; the free host follows from its own mass balance H0 = [H](1 + K11[G] + K11K12[G]^2), the very relation the guest cubic is derived from — exact, and mass-balance consistent by construction instead of two independently converged Newton solves. `test_nmr_any_equivalence` (which validates this model against nmr_any) and `test_varpro` unchanged. Remaining lead: `MinCubicRoot` computes all three roots when only the smallest positive one is used, and it is shared by the other fixed titration models.
